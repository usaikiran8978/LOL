# Decision & Ambiguity Log

Every ambiguity found in the BRD/TECH is recorded here with the decision taken. Nothing is omitted silently.

| ID | Topic | Ambiguity / choice | Decision | Rationale |
|---|---|---|---|---|
| DEC-001 | Product name | Documents give no product name | Working codename `amora`; package scope `@amora/*`. All user-facing branding comes from CMS/i18n so renaming is a config change. | Avoids hard-coding a brand |
| DEC-002 | Backend stack | TECH appendix: "FastAPI or NestJS; use one" | **NestJS + TypeScript** | One language across mobile, admin, API; contracts shared as zod schemas |
| DEC-003 | Data access | ORM vs SQL | Hand-written SQL migrations + **Kysely** typed query builder | Full control of pgvector, partial/GIN indexes, CHECK constraints, exclusion rules; no ORM magic |
| DEC-004 | Service topology | TECH §1 "independent services" vs appendix "Kubernetes only when justified" | Modular monolith with enforced module boundaries + outbox events; extractable later | See architecture §2 |
| DEC-005 | Mobile tooling | "React Native + TypeScript" | Expo (prebuild / bare-capable) | Faster delivery, native modules still possible |
| DEC-006 | Minimum age | BRD §6 "age eligibility" — no age given | Default 18, configurable per country in `country_configs.min_age` | Regional compliance |
| DEC-007 | Sensitive attributes | Religion, orientation, etc. | Stored as `sensitive` taxonomy; visibility per-field in privacy settings; excluded from AI prompts unless the user explicitly opts in; never in analytics payloads | Privacy by design (BRD §22, TECH §16) |
| DEC-008 | Location precision | "approximate location" not quantified | Exact coords only in `user_locations` (server-side). Others see city + bucketed distance (`<2 km`, `2–5`, `5–10`, `10–25`, `25–50`, `50+`). Geohash precision 5 for nearby queries | TECH §16 "exact location never exposed" |
| DEC-009 | Crossed paths | "where permitted" | Off by default; requires explicit opt-in consent + country flag; stores only coarse cell + hour bucket, retained 14 days | Legal exposure |
| DEC-010 | Question deletion | Prompt says "delete/archive" | Hard delete only for never-published drafts; published versions can only be archived (answers keep referencing them) | TECH §5 — never reinterpret history |
| DEC-011 | Answer re-use across versions | New version of a question | Admin chooses per version: `answer_carry_over = none | same_options | mapped` with explicit option mapping; otherwise users are re-prompted. Matching only compares answers via declared mappings | No silent reinterpretation |
| DEC-012 | Compatibility weights | Example formula in TECH §7 | Stored as **seed data** in matching config v1, editable by admin; code has no default weights | "do not hard-code them" |
| DEC-013 | Like/match model | Super-likes, rewinds | `swipe_actions` single table (like/pass/super_like) with unique (actor,target) + `rewound_at`; separate `matches` table | Simpler integrity; tables `likes/passes/super_likes` from TECH §4 exposed as views for traceability |
| DEC-014 | Payments | App-store vs Stripe | Billing provider abstraction with adapters: Stripe (web), Apple App Store, Google Play. Entitlements derived only from server-verified receipts/webhooks | TECH §17, "never rely on client-side status" |
| DEC-015 | AI provider | "provider-agnostic, OpenAI-compatible" | `AiProvider` interface; adapters for OpenAI-compatible HTTP and Anthropic. Provider keys from secrets; features disabled with clear error when no provider is configured | No fake AI |
| DEC-016 | Emergency escalation | BRD §15 "design" | Implement workflow: SOS → trusted contact notification (SMS/email) with coarse location link (opt-in exact for trusted contact only) + T&S urgent case; show local emergency number from `country_configs`. No direct emergency-service API | Varies by country |
| DEC-017 | Public ratings | Prompt forbids | Post-date feedback private, used only as model signal | BRD §16 |
| DEC-018 | Analytics store | Not specified | `analytics_events` in Postgres (partitioned monthly) + daily aggregate tables; export adapter for a warehouse later | MVP "basic analytics" |
| DEC-019 | Search | OpenSearch | `SearchIndex` interface: OpenSearch adapter (prod) and Postgres adapter (dev/test) | Local dev without OpenSearch |
| DEC-020 | Vector search | pgvector initially | `VectorStore` interface; migration creates `vector` columns only if the extension is available, else falls back to `real[]` + app-side scoring for dev | Local Postgres lacks pgvector |
| DEC-021 | BRD §4/§18/§23 headings empty in body | Content is in appendix tables | Appendix tables treated as normative for Target Users, Monetization tiers, MVP vs Phase 2 | |
| DEC-022 | MVP scope vs "build everything" | BRD §23 splits MVP/Phase 2; master prompt says build all | Build everything, ordered by TECH §24 delivery order; Phase-2 items ship behind feature flags | Both satisfied |
| DEC-023 | Prices & provider product IDs | Seed plans with prices? | Plans/entitlements are seeded; **prices are not** — they are entered in Admin → Billing with the real Stripe/App Store/Play product IDs | Seeding fake prices would ship wrong amounts or IDs that don't exist in the stores |
| DEC-024 | AI features at launch | Enabled by default? | All AI features are seeded **disabled** with no provider; enabling requires an admin to configure a provider, model and prompt version. Endpoints return `AI_NOT_CONFIGURED` until then, and clients fall back to non-AI behaviour | No fake AI (MP); cost control |
| DEC-025 | Apple receipt trust | JWS verification depth | App Store Server API JWS: x5c chain verified up to the **Apple Root CA – G3** fingerprint pinned in config (`APPLE_ROOT_FINGERPRINTS`) | Prevents forged signed transactions |
| DEC-026 | Identity verification provider | No vendor named | `VerificationProvider` interface; built-in `manual_review` routes submissions to the T&S queue. A vendor adapter (e.g. liveness/ID) can be added without API changes | Works on day one without a contract |
| DEC-027 | Event check-in codes | Store per-attendee codes? | Codes are HMAC-derived from `SIGNING_SECRET` + event + user: nothing stored, waitlist-promoted attendees always see theirs | No code table to leak or keep in sync |
| DEC-028 | Facebook login | Token type; trust of email | Accept classic user access tokens (Graph `debug_token` with app token + `/me` with `appsecret_proof`) and iOS Limited Login OIDC tokens. Facebook emails are **never** treated as verified, so a Facebook login cannot auto-link to an existing account; such accounts are identified by their social identity (`users.has_social_identity`, migration 0019) | Account-takeover protection |
| DEC-029 | Account deletion | Immediate vs grace; what remains | Re-auth (password, or session < 15 min) → immediate deactivation + sign-out → **purge after 14 days** (cancellable). Purge deletes personal rows and media, nulls message bodies, keeps an anonymized `users` husk (status `deleted`) so counterpart rows stay consistent. Device fingerprints are kept only for **banned** accounts (ban-evasion protection) | GDPR Art. 17 with a safety exception; protects people from accidental deletion |
| DEC-030 | DSAR handling | Deadlines, format | Due date 30 days (GDPR Art. 12; stricter regimes via `country_configs.privacy_regime`); export is a JSON bundle in object storage with a 7-day signed link; requests made outside the app are logged by support and executed with the same code | One code path for all channels |
| DEC-031 | Rate-limit storage | Multi-instance | Redis fixed-window counters (atomic Lua) when `REDIS_URL` is set; on Redis failure each instance falls back to memory limits instead of failing open or rejecting traffic | Availability without disabling protection |
| DEC-032 | Metrics exposure | Public `/metrics`? | `/metrics` requires `METRICS_TOKEN` (bearer, constant-time compare) and is disabled in production without one; labels use route templates only, never raw URLs | Raw paths can carry ids/PII; unauthenticated metrics leak internals |
| DEC-033 | Field-encryption key rotation | Key versioning | Ciphertext's first byte is the key version; current key + `FIELD_ENCRYPTION_RETIRED_KEYS` decrypt; `npm run db:rotate-encryption` re-encrypts all `ENCRYPTED_COLUMNS` (resumable, idempotent) | Key compromise must be recoverable without downtime |
| DEC-034 | Deployment target | Not specified (TECH appendix: "Kubernetes only when justified") | Containers (API, migrate job, admin) built once per commit; **reference** manifests for Kubernetes + GitHub environment approvals. Any container platform works; the manifests are a starting point | Needed for HPA + zero-downtime rollouts; platform choice stays open |
| DEC-035 | SLOs, RPO/RTO | BRD gives no numbers | Proposed: read p95 < 300 ms, write p95 < 500 ms, 99.9 % availability, RPO ≤ 5 min, RTO ≤ 1 h. Recorded as **proposals** in the runbooks for ops/product sign-off | Load tests need targets |
| DEC-036 | Dependency-audit gate | `npm audit` reports highs in Expo/Metro/Jest toolchains | CI blocks on **critical**; full report archived per run; runtime highs are fixed immediately (nodemailer upgraded 7 → 10). Toolchain highs tracked in progress.md | Blocking every PR on unfixable transitive dev-tool advisories would stop delivery without reducing risk |
| DEC-037 | Country scope (ABAC) coverage | Some admin endpoints checked scope, others didn't | One helper (`admin/auth/country-scope.ts`) applied to every endpoint that reads or changes a specific user (moderation cases/notes/actions/appeals/reviews, verification, billing lookup/grants/refunds, privacy requests, events by city). Out-of-scope targets answer 404 so existence isn't disclosed; lists are filtered | Found by the admin-console build; regression suite `review-fixes.e2e` |
| DEC-038 | Lifting bans | Reversal/appeal endpoints only required `moderation.action`/`moderation.appeals` | Reversing or overturning a `ban`/`unban` also requires `moderation.ban`, whichever endpoint does it | Privilege consistency |
| DEC-039 | SOS on an ended session | Mobile build flagged that SOS works after check-out | **Kept deliberately**: an emergency is never refused on a technicality; the trusted contact and T&S are alerted and the session reopens as `sos` | Safety over state hygiene |
| DEC-040 | Date-safety limits | Escalation delay, recheck window, contact cap, resend cooldown were constants | Admin-managed settings (`date_safety.*`, `date_safety.manage`, bounded) with seeded defaults 15 min / 30 min / 5 / 10 min | "Admin controls rules; nothing hard-coded" |
| DEC-041 | Event attendee visibility | Member list hides people not "open to meet"; organizers couldn't run check-in | Members see only open-to-meet attendees; the organizer and admins see the full roster. Check-in accepts the code alone (HMAC-derived per attendee, DEC-027) and asks for the attendee only on a collision | Privacy for attendees, practicality for organizers |
| DEC-042 | Google Play charged amounts | Play's subscription/product APIs don't return the price paid | Record the configured list price for that product (`billing_prices`) instead of 0; reconcile against Play financial reports for exact regional/tax amounts | Revenue reporting can't be 0; true amounts need the reports export |
| DEC-043 | Restore purchases | No restore endpoint | `POST /billing/restore` re-reads Google subscriptions server-side and rebuilds entitlements; App Store restore requires the device to re-send StoreKit transactions (`/billing/receipts/apple`); Stripe is webhook-driven | Each store's real capability |
| DEC-044 | AI output caches | Cached translations skipped consent and plan checks | Cache hits run the same access checks (configured, consent, entitlement) but don't count toward usage limits | Consent withdrawal must apply immediately; cached results cost nothing |
| DEC-045 | Realtime event shapes | `match.ended` had two payloads (block vs unmatch) | One payload `{ matchId, conversationId }` sent to both people; a block is indistinguishable from an unmatch for the blocked person. `message.updated` is emitted when media moderation finishes; removed messages reach the other members as `message.deleted` | Clients handle one contract; blocks stay private |
| DEC-046 | User-facing copy in server code | A few notifications/emails still had English literals | Every user- or contact-facing message now comes from a seeded, admin-editable template (event cancelled/approved/rejected/updated/waitlist/checked-in, trusted-contact resolved/invite in the member's locale, admin invite). Remaining literal: the internal on-call T&S alert email (staff-only operational alert) | Localization rule; staff alert documented as exception |
